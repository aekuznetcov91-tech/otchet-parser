   ```bash
   cp ~/Downloads/DEAL_*.xls .
   ```

   ```bash
   python3 scripts/parser_engine.py
   ```
3. Скрипт автоматически найдет свежие файлы, проведет дедупликацию, пересчитает выручку без НДС, сопоставит партнеров по Master ID и обновит `site/data.json`.
4. Пересобрать витринную Excel-таблицу:
   ```bash
   python3 scripts/build_showcase_q3_unified_excel.py
   ```

Перед любым коммитом или деплоем обязательно прогнать тесты (с локальным Node в PATH):


## 4. ПРАВИЛА РАБОТЫ И ИНВАРИАНТЫ КОДОВОЙ БАЗЫ

1. **🚨 Синхронизация Git и Cloudflare:**
   - Всё, что деплоится на Cloudflare Pages, **ОБЯЗАТЕЛЬНО** коммитится и пушится в Git (`origin main`). Никаких рассинхронов между локальной разработкой и репозиторием.
2. **Модульность JavaScript:**
   - Запрещено переносить логику обратно в `site/index.html`. Все доработки вносятся строго в модули `site/js/*.js` (`charts.js`, `tables.js`, `debtors.js`, `funnel.js`, `lead-geo.js`, `kam-dashboard.js`, `utils.js`).
3. **Master Partner Registry:**
   - Редактирование привязок дилеров осуществляется через `data/partners_registry.json`. При изменениях обязательно запускать `python3 scripts/parser_engine.py` для обновления боевых файлов.
4. **Формат ссылок BFS:**
   - Прямой адрес на карточку клиента в CRM Backoffice строго формируется по шаблону:
     `https://backoffice.x.sberauto.com/crm/manager/{client_id}`
5. **Финансовая модель:**
   - Комиссия СберАвто = 2% от суммы ДКП.
   - Выручка без НДС = `Комиссия / 1.22`.
   - Опт МП2 (Wholesale, холд 1 000 ₽) **СТРОГО ИСКЛЮЧЕН** из розничной воронки конверсий.
6. **Определение «Крыши» (Rooftop):**
   - 1 «крыша» = 1 бренд в 1 городе конкретного дилера.
   - Активная крыша = $\ge 1$ закрытая сделка за месяц.


## 5. Рефакторинг и выпуск (03.10.2026)

### Единственный источник фронтенда

Редактируйте `site/index.html`, `site/css/*.css` и `site/js/*.js`.
Исключение: `site/js/kam-dashboard.js` — генерируемый совместимый файл.
Его исходники находятся в `site/js/kam/`: `defaults`, `normalization`, `access`,
`plans`, `filters`, `aggregation`, `render`, `reports`.
`calculateKamAggregation(payload, filter, options)` получает данные, планы,
КАМ-фильтр, месяц нормализации брендов и дату явно. `getKamAggregatedData`
сохраняет прежний интерфейс и читает состояние браузера.

После правок выполните:

```bash
python3 scripts/sync_frontend.py
python3 scripts/sync_frontend.py --check
```

Скрипт соединяет КАМ-модули в фиксированном порядке без транспиляции,
синхронизирует корневые `js/`, `css/`, `index.html` и обновляет версии ресурсов
в HTML по SHA-256 содержимого. Корневые копии вручную не редактируются.
Webpack/Vite, npm-сборка и загрузчики модулей не требуются.
Боевая ленивая загрузка `banking_deals.json` сохранена и перенесена в корневую копию.

### Этапы ETL

`python3 scripts/parser_engine.py` остаётся точкой входа. Старые публичные функции
доступны через совместимые импорты из этого файла. Реализация — в `scripts/etl/`:

- `sources.py`, `tabular.py`: обнаружение и чтение входных файлов;
- `normalization.py`: ключи, бренды, даты и VIN;
- `history.py`: объединение выгрузок с историческим кэшем;
- `partners.py`, `transactions.py`: закрепления, сделки, лиды и должники;
- `funnel.py`, `analytics.py`, `lead_geo.py`, `payload.py`: аналитика и итоговый payload;
- `export.py`: атомарная замена JSON без предварительного удаления старого файла;
- `config.py`: пути относительно текущего проекта.

При сравнении старого и нового ETL запускайте их в отдельных копиях с одинаковыми
источниками и `PYTHONHASHSEED=0`. Существующая геоаналитика использует встроенный
`hash()` для части распределения, поэтому без фиксированного seed результат
между процессами может отличаться. Эта бизнес-логика при рефакторинге сохранена.

```bash
python3 scripts/compare_etl_outputs.py /path/to/before /path/to/after
```

Сравниваются пять выходных JSON, включая историю и реестр. Игнорируются только
`metadata.updated_at` и `banking_analytics.updated_at`.

### Публикация

Только Git (без запуска Cloudflare):

```bash
python3 deploy_to_cloudflare.py --git-only --message "refactor: modular dashboard and verified releases"
```

Git и Cloudflare Pages:

```bash
python3 deploy_to_cloudflare.py
```

Порядок: синхронизация фронтенда → проверка размеров → полный unittest → проверка
ветки `main` и отсутствия расхождения с `origin/main` → проверка staged-файлов на
секреты → коммит → push → сверка удалённого SHA → публикация архива `site/` именно
из этого коммита. Локальные неотслеживаемые файлы в архив не попадают.
Ошибка команды, таймаут или несовпадение SHA останавливают выпуск с ненулевым кодом.
Автоматический rebase после публикации удалён. Если Cloudflare отказал после push,
коммит остаётся в Git, но выпуск не объявляется успешным; причину нужно устранить
и повторить команду. Дополнительные remote автоматически не публикуются.

## 6. Фактическая аналитика калькулятора и воронки (03.10.2026)

Google Apps Script калькулятора читается **только GET**. URL задаётся ключом
`calculator_analytics_url` в игнорируемом `config.local.json` либо переменной
`CALCULATOR_ANALYTICS_URL`. Обновление перед каждым выпуском данных:

```bash
python3 scripts/sync_calculator_analytics.py
python3 scripts/refresh_funnel.py
python3 scripts/sync_frontend.py
python3 deploy_to_cloudflare.py
```

При полном обновлении сделок после `sync_calculator_analytics.py` запускайте обычный
`parser_engine.py` вместо `refresh_funnel.py`. Последний изменяет только
`brand_funnel` в двух data.json, не трогая сделки, историю, реестры и другие блоки.
Парсер использует сохранённый снимок; сетевых запросов при агрегации нет.
Для локального JSON-экспорта предусмотрен `sync_calculator_analytics.py --input PATH`.
Ошибка API/пустой или некорректный ответ останавливает обновление снимка.

В Git хранится только агрегат `data/calculator_analytics.json`: события, число
уникальных корректных ClientId и события без ID, отдельно по месяцам/брендам.
Исходные журналы с клиентскими ссылками в Git и site/ не добавлять.
Повторные расчёты — отдельные события; точные дубли строк исключаются.
Сводные уникальные клиенты вычисляются объединением ID, не суммой брендов/месяцев.
Бренд берётся из `details.car` или `details.brand`, иначе «НЕ ОПРЕДЕЛЁН».
С сентября OMODA/JAECOO относятся к JELAND. Диапазон и время снимка видны в UI;
это сохранённый снимок, а не онлайн-поток. Первый/последний месяцы могут быть неполными.

В брендовой воронке удалены все коэффициенты, вымышленные лиды, фиксированные даты
и фиктивный матчинг 40%. Расчёты/офферы/анкеты — фактические логи Google.
Квалификация — наблюдаемый порядок «Новый лид → Закрепление менеджера» в CRM;
передачи — уникальные ClientId из `sys_db_partners` с `Type == Лид`.
Заполненная анкета ФДЦ не считается заявкой/одобрением банка. Подтверждённого
источника отправленных в банк заявок пока нет; UI показывает «Нет данных».
Отсутствие CRM-событий также не подменяется нулём. Ноль в покрытом журналом
периоде означает отсутствие зарегистрированных событий, не доказательство
отсутствия действий. Периоды до начала Google-журнала недоступны.

Показатели источников не являются единой когортой: коэффициенты сквозной конверсии
и отвалов между ними не показываются. Розница: Передача лида, ФДЦ + ФДЦ+ГП, Online;
МП1/2/3 и сделки без канала исключены. PostHog сохранён как отдельный источник.
Проверки: unit-тесты и `tests/funnel_browser.cjs` (тот же Playwright, что browser_smoke.cjs).
